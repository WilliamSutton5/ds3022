  The concepts, line by line:
  - The API request: httpx.get(URL, headers=..., params=...) sends an HTTP GET.
    headers carries your token, so the token is only ever read from GH_PAT.
    params is a dictionary that httpx turns into a query string, so the actual
    URL becomes .../commits?per_page=100.
  - raise_for_status(): httpx doesn't treat a 401 (bad token) or a 403 (rate
    limit) as an error by default. This line turns those into an
    httpx.HTTPStatusError. That error fails the task, so Prefect's retries=3
    kick in. Without it, we'd try to parse an error message as if it were
    commits.
  - JSON parsing: response.json() converts the response text into Python
    objects. GitHub returns a JSON array of objects, so commits is a list of 
    dictionaries.
  - Nested dictionary access: each commit is nested several levels deep. For
    example:
  c = {"sha": "a1b2c3d4...", "commit": {"author": {"date": "2026-10-14T..."},
  "message": "Fix bug\n\nDetails..."}}
  c["commit"]["author"]["date"]       # "2026-10-14T..."
  c["commit"]["message"].splitlines()[0]   # "Fix bug"  (first line only)
  c["sha"][:7]                         # "a1b2c3d"  (string slicing)
  - The next link: GitHub sends a Link header that points to the following page,
    and httpx parses it into response.links, a dict of dicts. .get("next", {})
    returns {} instead of crashing when there's no next page, so the chained
    .get("url") safely returns None. Step 4 builds the loop around this line.

  The concepts:
  - The while loop with two stop conditions: while url and page <= PAGES keeps
    going only while both are true. url becomes None when GitHub sends no next
    link (the real last page), and None counts as false. page <= PAGES stops
    after 10 pages, because git/git has tens of thousands of commits and we
    don't want all of them.

    values from one pass to the next:

  |------|-------------------------|-------------------|----------------|
  | 1    | .../commits             | {"per_page": 100} | 2              |
  | 2    | ...?per_page=100&page=2 | None              | 3              |
  | …    | …                       | …                 | …              |
  | 10   | ...&page=10             | None              | 11 → loop ends |

    already includes it, so params = None avoids adding it twice.

    extend adds each item, while append would add the whole list as one item:

    whole task, and Prefect reruns it from page 1. Since nothing is written to

  The concepts:
  - The database connection with with: duckdb.connect(DB_FILE) opens
    05_prefect/actions.duckdb, creating it if it doesn't exist. The with block
    closes the connection when the block ends, even if an error happens, so you
    don't leave a lock on the file. That's what the global conn we removed in
    Step 2 lacked.
  - Option (a), CREATE OR REPLACE TABLE: each run drops the old commits table
    and creates an empty one, so a rerun or a Prefect retry can never stack
    duplicates. It always leaves just this run's 1,000 rows. In a schema, sha 
    VARCHAR PRIMARY KEY means each sha must be unique. If a duplicate ever got
    into rows, the insert would fail loudly instead of quietly storing it twice.
    TIMESTAMPTZ is where DuckDB turns the ISO date string from Step 5 into a
    real timestamp.
  - The f-string vs $ placeholders: these do two different jobs.
    - f"...{TABLE}..." is Python string formatting, which inserts our own
      constant commits into the SQL text.
    - $sha, $author_name, ... are parameters: DuckDB fills them from each
      dictionary by matching key names. For example, {"sha": "a1b2…", 
      "author_name": "Junio C Hamano", ...} fills $sha with "a1b2…". We never
      paste API data into SQL text ourselves. That protects against strange
      characters, such as a commit message containing ', and against SQL
      injection.
  - executemany: it runs the INSERT once per dictionary in rows, so 1,000
    inserts in one call. It's the database version of a for loop.
  - The count query: .fetchone() returns the first result row as a tuple, like
    (1000,), and [0] takes the number out of it.
